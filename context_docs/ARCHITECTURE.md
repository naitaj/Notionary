# Notionary System Architecture

## 1. System Overview

**Notionary** is an AI-powered project reasoning layer designed to bridge the gap between unstructured team discussions (transcripts, meeting notes, RFCs) and structured knowledge bases (Notion databases, execution trackers, and decision logs).

Rather than acting as a passive document wiki or a simple text search engine, Notionary transforms documentation into a **typed, directional knowledge graph** that tracks rationale provenance, propagates change blast radii, continuously monitors contradiction and evidence sufficiency, and powers verifiable **Graph-RAG Q&A**.

## 2. Core Subsystems

### 2.1 Storage & Entity Graph Layer
The underlying storage is powered by **SQLite** using `WAL` (Write-Ahead Logging) mode and async sessions via `SQLAlchemy 2.0`.
The schema defines 15 interconnected entities:
- **Projects**: The root workspace container.
- **Documents & Chunks**: Source text with heading hierarchies, character offsets, and SHA-256 content hashes.
- **Decisions**: Formal choices (`D-17`) with versioning, rationale, status, and supersession links.
- **Tasks**: Action items (`T-14`) with status, owner, blocked reasons, and `origin_decision_id`.
- **Experiments & Results**: Empirical runs (`EXP-06`) capturing quantitative metrics, units, baselines, and variance.
- **Claims**: Verifiable propositions tagged with metric, subject, condition, and sufficiency taxonomy.
- **Milestones & Deliverables**: Project roadmap markers with risk evaluations.
- **Edges**: Directional, typed relationships (`supports`, `resulted_in`, `contradicts`, `depends_on`, `supersedes`).
- **Contradictions**: Discrepancies surfaced by the reasoning radar between claims or results.
- **Proposals**: Structured staging items generated by extraction AI before human confirmation.
- **Weekly Reports**: Automated executive intelligence digests.

### 2.2 Extraction & 3-Tier Review Routing
To eliminate LLM hallucinations while avoiding human fatigue, extracted proposals pass through a **3-tier confidence gateway**:
1. **High Confidence (`>= 0.85` or exact pattern match)**: Staged as auto-approved draft or fast-track review.
2. **Medium / Low Confidence (`0.60 - 0.84`)**: Flagged for human review in the **Review Inbox** with source text excerpts highlighted.
3. **Unreviewed / Suspect (`< 0.60`)**: Quarantined from the evidence graph; will not influence RAG or impact analysis until human approval.

### 2.3 Hybrid Search & Graph-RAG Q&A
When answering "Why did we choose X?", Notionary executes a hybrid pipeline:
1. **Keyword Retrieval**: SQLite FTS5 runs BM25 lexical search over chunk text.
2. **Dense Semantic Retrieval**: Cosine similarity against document chunk embeddings.
3. **Reciprocal Rank Fusion (RRF)**: Merges lexical and dense candidate sets with $k=60$.
4. **Graph Subgraph Expansion**: From top matched nodes, traverses 2 hops along `supports` and `resulted_in` edges to collect structured context (e.g. linking Decision D-17 to Experiment EXP-06).
5. **Cited Synthesis**: The LLM synthesizes the final answer accompanied by explicit citation pointers referencing chunk IDs, document titles, and character offsets.

### 2.4 Bidirectional Notion Sync
Notionary synchronizes bidirectional state with Notion workspace databases:
- **Push Engine**: Enqueued background jobs push approved decisions, tasks, and reports to Notion database pages with relation properties intact.
- **Pull & Conflict Resolution**: Compares incoming page `last_edited_time` and `SHA-256` content hash against local record dirty states:
  - If only remote changed: Local state updates automatically.
  - If only local changed: Remote page updates.
  - If both changed (concurrent conflict): System retains both versions and logs a conflict resolution proposal for human sign-off.

### 2.5 What-If Impact Analysis Engine
When a decision is modified or revoked:
1. Runs directional graph traversal starting at `decision_id`.
2. Follows `resulted_in`, `depends_on`, and `affects` edges up to depth $N$.
3. Identifies invalidated downstream tasks, deliverables at risk, and affected experiments.
4. Generates a blast-radius manifest with suggested remediation actions.
5. On approval, atomic transaction updates task flags (`needs_reevaluation = true`) and creates re-evaluation tasks.

### 2.6 Resilience & Demo Hardening Layer
To guarantee rock-solid demo performance:
- **ResilientLLMProvider**: Wraps all generative calls with an enforced **15.0s timeout** (`asyncio.wait_for`).
- **Prompt Hash Cache**: SHA-256 prompt hashing provides sub-millisecond response for recurring queries.
- **Deterministic Golden Fallbacks**: In the event of network disruption or provider throttling, the system seamlessly falls back to pre-computed canonical mock responses without throwing user-facing 500 errors.
